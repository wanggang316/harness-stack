# 项目知识

长期文档帮助没有参与历史讨论的人理解系统并正确修改。按知识主题组织当前说明，按决定保留理由，按任务记录交付。文件按需创建，不要求每次修改产出文档。

## 三类记录

| 类别 | 回答的问题 | 维护方式 |
| --- | --- | --- |
| 当前知识 | 系统如何工作、承诺什么、如何操作 | 随相关变化原位更新 |
| 决策记录 | 在什么约束下为何这样选，接受什么代价 | 保留背景，明确有效状态与替代关系 |
| 交付记录 | 本次要改什么、进展如何、验证了什么 | 执行中更新，完成后关闭或归档 |

契约表示应当成立的规则，实现说明表示当前机制，两者冲突需要判断原因。实现、合并、部署和运行验证是不同状态；历史测试结果只证明当时版本和环境下的观察。

## 知识入口

沿用项目已有目录、语言与索引。没有约定时，可按需使用 `docs/index.md`、`docs/glossary.md`、`docs/architecture.md`、`docs/domains/`、`docs/decisions/` 和 `docs/runbooks/`。小项目可先用 README；不建立空目录或平行词汇表。

领域文档是行为与边界的主要维护位置。全局架构说明跨模块关系，ADR 保存理由，runbook 保存可执行步骤。用链接连接证据和决定；同一项规则只有一个主要维护位置。

`AGENTS.md` 保留工作约束和条件式入口。例如修改认证时读认证领域文档，准备发布时读发布 runbook。历史记录不进入默认阅读路径。

## 变更生命周期

1. 开工时读取相关当前知识和有效决定。复杂取舍用 proposal，普通改动用任务描述即可。
2. 执行状态、偏差及验证证据放在任务或 PR；只在交接或复杂迁移需要时另写执行记录。
3. 修改行为、架构或操作方式时，同时更新相关长期知识；重要的新理由记录为 ADR。没有长期知识变化时无需新增文档。
4. 交付后关闭 proposal，附交付证据与当前知识链接。已关闭方案保存原背景，不随未来产品变化不断改写。

## 独立能力

- `design`：形成、修订或关闭复杂变更方案。
- `document`：将已确认变化落实到最小的长期知识集合。
- `audit-docs`：检查准确性、可发现性和保留价值，修复有证据的问题。
- `domain-modeling`：在讨论中澄清概念并及时记录确定的术语和决定。

这些能力不构成强制流水线。日常开发可直接修订相关文档，审计也不要求存在 proposal 或历史 ticket。

## 保留与淘汰

优先保存业务语义、不变量、跨模块关系、不明显的决策理由、操作与恢复知识，以及难以重新发现的经验。普通调试经过、逐文件变更清单、易查询的配置值无需复制进长期知识。

删除内容前确认它没有独有的解释或历史价值；未知不等于错误。退役的当前说明退出当前入口，被替代的决定保留来源与替代指针。未解决的契约冲突明确报告，不以整理文档为由改变产品规则。

检验入口是否有效：新上下文能否找到某领域的概念、行为约束、修改影响和决策理由，而无需按时间重读交付历史。
