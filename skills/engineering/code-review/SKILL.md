# code-review

检查一组明确的改动，交付可定位、可验证的 findings 和评审结论。评审期间保持被评审文件不变；修复、发布评论和合并属于另外的授权范围。

## 固定评审对象

先确认工作目录、分支、基点、提交范围和工作区状态。用户指定的范围优先；PR 使用其实际 base/head，分支评审使用与目标分支的 merge-base。明确的两端提交比较使用两端 diff，不把它改成 merge-base 比较。将分支名解析为 SHA，避免评审中移动的引用改变对象。

评审进行中的实现时，包含约定范围内的 staged、unstaged 和 untracked 文件。已跟踪文件可用 `git diff <base-sha>` 查看最终工作区相对基点的净变化，再结合 `git diff --cached`、`git diff` 和 `git ls-files --others --exclude-standard` 核对组成。新文件单独读取；区分用户原有改动，范围不明就确认归属，不自动纳入或清理。

记录 base/head、文件清单及未提交部分的内容快照或哈希。异步评审时暂停这些文件的写入，或提供隔离快照；结束前核对身份，发生变化就注明覆盖失效并补审，不能把旧报告套到新代码上。

若引用无效、基点无法确定或约定范围内没有改动，报告实际情况并请求必要的范围信息。空 diff 不产生批准结论。

## 建立评审依据

从用户要求、任务正文、PR 描述和相关当前知识确定预期行为；读取受影响目录的项目指令、规范、有效决定和测试。没有独立 spec 文件时可使用已确认的任务描述。缺少需求依据不阻止检查可证实的代码问题，但需求符合度须标为未验证。

分别回答两类问题：改动是否完成约定行为；实现是否正确且符合项目约束。项目规范优先于个人偏好。结构、命名和抽象建议需解释实际维护成本或错误风险，不能单凭函数长度、参数数量或抽象层数判定缺陷。

## 沿行为路径检查

先看测试与断言揭示的行为，再沿改动追踪输入、状态变化、输出和失败路径。读取必要的 diff 外代码，包括调用方、枚举消费者、授权边界、持久化约束和迁移流程，确认问题是否真实可达。

检查以下风险在本次改动中是否成立：

- **行为与契约**：遗漏需求、错误状态转换、边界输入、错误恢复、重复调用、并发及兼容性。
- **测试与证据**：断言是否能发现目标错误，是否仅验证替身，已有测试是否覆盖新路径。没有新增测试不是自动 finding；指出具体未守住的行为及回归风险。
- **设计与知识**：责任边界、调用方迁移、不必要的复杂度，以及因改动失效的说明和操作步骤。
- **安全与资源**：不可信输入的使用、权限与租户隔离、敏感信息、副作用、资源释放和有实际负载依据的性能风险。

需要展开某类风险时读 [评审检查参考](../../../references/review-checklist.md)。清单帮助形成假设；每条 finding 仍须回到当前代码证明。

必要时运行安全、聚焦的检查或复现。区分作者提供的证据与自己执行的结果；完整测试套件、UI 验收和线上行为没有实际执行就不声称通过。第三方 API、依赖或安全事实有疑问时核实对应版本的权威资料。

## 写可行动的 findings

每条 finding 给出严重度、当前版本的 `file:line`、触发条件、具体影响及证据。引用尽量指向引入问题的最小位置；若问题体现在调用方，说明与改动的因果关系。给出修复方向即可，只有代码片段确实帮助消除歧义时才附代码。

| 严重度 | 判断依据 |
| --- | --- |
| Critical | 可证实的严重安全、数据完整性或核心功能损坏，必须解决 |
| Important | 必需行为遗漏、实际回归或有明确影响的设计与验证缺口，需要修复或有权者明确接受风险 |
| Suggestion | 有具体收益的改进，当前改动可以不采纳 |
| Nit / FYI | 局部润色或背景信息，仅在有帮助时报告 |

严重度由触发条件和影响决定。未核实的怀疑列为待确认问题，写明缺少什么证据；不靠置信度数字把猜测包装成事实。既有问题与本次引入或加重的问题分开，避免要求本次顺手修完历史债务。

合并同一根因的重复 findings，按影响排序，同时保留“需求”或“实现/规范”的归属，避免一个维度的通过掩盖另一个维度的缺口。没有实际问题时可以报告没有 findings。

## 交付评审

报告包含：

- **范围与依据**：base/head、未提交部分、需求来源，以及独立评审或作者自检的身份。
- **Findings**：已核实问题与待确认问题分开。
- **验证与限制**：检查过的路径、实际命令和结果、未覆盖范围。
- **结论**：`Request changes` 表示存在未解决的 Critical / Important；`No blocking findings` 表示约定范围审完且未发现阻塞问题；`Incomplete` 表示关键范围或依据不足。没有需求依据时仍可报告代码 findings，但整体结论不能暗示需求已验收。

存在已证实的阻塞问题且另有未覆盖部分时，给出 `Request changes` 并列明限制。`No blocking findings` 是评审结果，不代表测试、合并、部署或线上验收完成。用户要求发布到 PR 时才发布，并核对目标 PR 与评审版本一致。
